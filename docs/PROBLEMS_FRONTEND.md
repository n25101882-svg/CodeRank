# Problems Management Frontend — практична №9, етап 2

У гілці `feature/problems-management` додано захищений маршрут `/problems` на HTML/CSS/Vanilla JavaScript у наявному Vite SPA. Є список власних задач, створення, редагування після окремого GET за Id, видалення з діалогом підтвердження, Loading/Success/Empty/Error та повторне завантаження. Темну палітру й лаймові акценти CodeRank збережено; навігація «Мій профіль / Мої задачі» працює з Dashboard і на мобільних екранах.

Backend CRUD та його ручну перевірку в `CodeRankAuthTest` підтвердив користувач після етапу 1. **Нову Frontend → Backend → MSSQL інтеграцію на цьому етапі не виконували.** Автоматизовані Frontend-тести повністю перехоплюють API, Backend-тести використовують SQLite in-memory.

## Контракт і поведінка

Усі Problems-запити виконуються на `VITE_API_BASE_URL` (типово `https://localhost:7160`) з `Authorization: Bearer TOKEN`. Відсутній токен не допускає відкриття сторінки. HTTP 401 від будь-якої з п’яти операцій очищає клієнтську сесію та відкриває Login. Токен не додається до URL або localStorage.

| API | Дія Frontend | Очікуваний успіх |
|---|---|---|
| GET `/api/v1/problems` | Завантажити або оновити список | 200, масив DTO; `[]` — Empty |
| GET `/api/v1/problems/{id}` | Завантажити свіжі значення для редактора | 200, DTO |
| POST `/api/v1/problems` | Створити задачу | 201, DTO |
| PUT `/api/v1/problems/{id}` | Зберегти редаговані поля | 204, без тіла |
| DELETE `/api/v1/problems/{id}` | Видалити після підтвердження | 204, без тіла |

HTTP-клієнт явно задає метод і перевіряє очікуваний статус. Для 204 він повертає результат без читання JSON. Після успішного POST/PUT/DELETE виконується новий GET списку без перезавантаження документа. Якщо запис успішний, але цей GET не вдався, повідомлення про збереження залишається видимим разом з окремою помилкою списку та кнопкою повторення. Це не пропонує повторно створювати вже збережену задачу.

JSON запису містить тільки `title`, `statement`, `inputFormat`, `outputFormat`, `difficulty`. `id`, `createdByUserId`, `createdAtUtc` та інші поля не передаються. Title обрізається по краях і має містити 1–200 UTF-16 одиниць; Statement не може бути порожнім/пробільним. Умова та непорожні формати зберігають пробіли й переноси рядків. Порожні необов’язкові поля стають null; Difficulty — null/Easy/Medium/Hard. Перевірки на Backend залишаються остаточними.

Назва, умова, формати й назва в діалозі видалення вставляються через `textContent`, значення редактора — через `.value`. Відповіді API перевіряються перед відображенням та очищаються від зайвих полів. Кнопки й форма блокуються під час операції; незавершені запити отримують AbortSignal поточного маршруту.

HTTP 400 показує безпечні повідомлення та помилки відомих полів; 404 пропонує оновити список; 409 у діалозі пояснює прив’язку до олімпіади та залишає задачу на місці. Для 500, мережевих збоїв, некоректного DTO та таймауту є зрозумілі повідомлення, відновлення контролів і можливість повторення. Сирі повідомлення SQL/API не показуються. Перед підтвердженням видалення також зазначено чинне каскадне видалення `ProblemExamples` у БД.

## Development CORS

У наявній політиці `FrontendDevelopment` додано PUT і DELETE до GET/POST. Origin залишається тільки `http://localhost:5173`; заголовки — Content-Type/Authorization, credentials не дозволяються. Політика реєструється й застосовується лише в Development. JWT, CRUD-контролер, моделі, SQL та міграції на цьому етапі не змінено. Для роботи з новим CORS потрібно перезапустити локальний Backend.

## Локальний запуск і ручна інтеграційна перевірка

Використайте наявні безпечні налаштування Backend для погодженої `CodeRankAuthTest`; User Secrets цією реалізацією не змінювалися. У двох терміналах з кореня репозиторію:

```powershell
dotnet run --project backend/CodeRank.Api --launch-profile https
```

```powershell
cd frontend
npm run dev
```

Браузер має довіряти локальному HTTPS-сертифікату. Перевірте API Base URL та що Frontend відкритий саме на `http://localhost:5173`. SQL-дозволи для CRUD наведено в [PROBLEMS_API.md](PROBLEMS_API.md).

Наступні кроки призначені для ручної перевірки користувачем і **не виконувалися автоматично з MSSQL**:

1. Без сесії відкрийте `/problems`: очікується Login. Увійдіть наявним тестовим акаунтом та відкрийте «Мої задачі»; список має містити лише його задачі. Перевірте F5 та мобільний viewport.
2. Створіть власну тестову задачу через форму. У Network очікується POST 201, потім GET списку 200. Перевірте відсутність серверних полів у JSON запиту. Не копіюйте JWT у звіт чи Git.
3. Натисніть «Редагувати»: очікується GET за Id. Змініть умову/формати/складність; після PUT 204 список має оновитися новим GET.
4. Для видалення спочатку перевірте «Скасувати», потім підтвердження на власній тестовій задачі, яку дозволено видалити. Очікується DELETE 204 і GET оновленого списку. Врахуйте видалення прикладів за чинним правилом БД.
5. Якщо вже є власна задача, пов’язана з олімпіадою, перевірте 409 та збереження задачі. Спеціальні зв’язки чи інші записи SQL автоматично не створюються.
6. Для відмови API тимчасово заблокуйте потрібний запит у DevTools, потім відновіть доступ і оновіть список. За 401 сторінка повинна очистити сесію та відкрити Login.

## Відомі обмеження

- Наскрізний ручний CRUD через новий Frontend із MSSQL ще потрібно виконати; підтвердження Backend-етапу не заміняє його.
- Незбережена форма живе лише в пам’яті сторінки; F5/перехід можуть втратити введені дані. Пагінацію та захист від конкурентного редагування не додавали.
- Скасування або таймаут клієнтського запиту не гарантує відкат уже виконаного запису на сервері. Перед повторним POST після невизначеного результату слід оновити список.
- Збережено sessionStorage-модель JWT: вона доступна JavaScript; Logout очищає клієнтську сесію й не відкликає токен на сервері. Перевірено безпечний DOM-рендеринг конкретних полів, а не повний XSS-аудит.
- API-клієнт відхиляє числові Id поза діапазоном безпечних цілих JavaScript, щоб не змінити іншу задачу через втрату точності.
