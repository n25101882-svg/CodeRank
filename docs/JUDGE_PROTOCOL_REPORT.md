# SCRUM-10 · етап 1. Протокол Judge Worker і черга

Цей звіт фіксує етап 1. Поточну інтеграцію Worker, IPC та її QA описано окремо. [Stage 2B2](JUDGE_STAGE_2B2_REPORT.md)

Гілку `feature/judge-worker-protocol` створено від `develop` після PR №16. ASP.NET Core API на PentiumServer володіє чергою в MSSQL. Окремий .NET Worker під’єднується до API вихідним HTTPS-з’єднанням, отримує метадані завдання й підтримує lease. Компіляція та виконання C++17 і Python 3 належать наступному етапу. [SCRUM-10](https://coderank.atlassian.net/browse/SCRUM-10)

## Контракт API

Базовий шлях `/api/v1/judge/jobs`. Кожен запит передає `X-CodeRank-Worker: <worker-id>` та `Authorization: CodeRankJudge <key>`. JSON використовує camelCase. Для heartbeat і complete передавай `Content-Type: application/json`. Дата завершення lease подається в UTC, а відповіді мають `Cache-Control: no-store`.

| POST | Тіло | Успішна відповідь |
| --- | --- | --- |
| `/claim` | Порожнє | `200` з `{ id, problemId, language, leaseToken, leaseExpiresAtUtc }` або `204`, коли доступних завдань немає. Мови `cpp17` і `python3`. |
| `/{id}/heartbeat` | `{ "leaseToken": "<uuid>" }` | `200` з `{ leaseExpiresAtUtc }`. |
| `/{id}/complete` | `{ "leaseToken": "<uuid>", "verdict": "<final-status>" }` | `204` під час ізольованих автоматизованих тестів, зокрема при повторі вже збереженого вердикту. Звичайний API етапу 1 відповідає `403 judge_execution_disabled`. |

Claim містить лише метадані завдання. Вихідний код і приватні тестові дані під’єднуватимуться до протоколу після перевірки sandbox. Службові поля lease відсутні в контрактах студентської історії.

`400` означає некоректне тіло, зайві поля або недопустимий статус. Claim із тілом також дає `400`. Для heartbeat і complete діє ліміт тіла 1 КіБ, перевищення дає `413`. `401` означає, що Judge API вимкнений, облікові дані недійсні або запит надійшов по HTTP. Дійсні Student і Admin JWT також отримують `401`. `409 lease_lost` повертається для невідомого ID, чужого токена чи простроченого lease. `409 verdict_conflict` означає спробу змінити збережений вердикт тією самою видачею. Тимчасова недоступність блокування черги дає `503` з `Retry-After: 5`.

## Життєвий цикл

| Подія | Результат |
| --- | --- |
| Claim | Застосунок спочатку відновлює прострочені видачі, потім бере перший `Queued` за ID. Спроба стає `Running`, лічильник видач зростає на один. Сервер генерує новий UUID та lease на 60 секунд. |
| Повтор claim від того самого Worker | Поки його lease чинний, повертаються ті самі ID, токен і термін. Це дає змогу відновитися після втрати HTTP-відповіді або перезапуску. Одна ідентичність Worker відповідає одному активному процесу. |
| Heartbeat | Поточний власник із чинним токеном продовжує lease до `now + 60 с`. Повтор з тією самою серверною позначкою часу зберігає той самий термін. |
| Закінчення lease | Видача чинна за умови `now < leaseExpiresAtUtc`. Після спливу терміну наступний claim повертає спробу в чергу й може видати її з новим токеном. Після третьої простроченої видачі встановлюється `SystemError`, попередні реквізити lease очищаються. |
| Завершення в тестах | Лише власник чинного lease переводить `Running` у фінальний статус. Сервер фіксує час завершення й залишає власника та токен для розпізнавання повтору. Той самий результат повертає `204` і зберігає первинний час завершення. |

Валідні фінальні статуси вже визначені в `Submissions`. Це `Accepted`, `WrongAnswer`, `CompilationError`, `RuntimeError`, `TimeLimitExceeded`, `MemoryLimitExceeded` і `SystemError`. Політика запису вердиктів у штатному хості фіксовано вимкнена. Її підмінює лише тестовий хост на синтетичних даних.

На SQL Server усі зміни черги отримують `Exclusive` application lock `CodeRank.JudgeQueue.v1` із власником `Transaction`. Блокування діє в межах однієї БД, спільно для екземплярів API. Час зчитується через `SYSUTCDATETIME()` після отримання блокування. Транзакція охоплює відновлення, вибір і запис. Якщо транзакція обривається, SQL Server відкочує зміни та звільняє блокування. Унікальний фільтрований індекс додатково обмежує кількість виданих `Running` до одного на Worker. [Блокування SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql?view=sql-server-ver17)

## Конфігурація та загрози

Judge API за замовчуванням закритий для машинних запитів. Для дозволеного ізольованого QA задай `Judge__Enabled=true`. Увімкнений API перевіряє машинну конфігурацію до підключення до БД. Worker також завершує запуск, якщо бракує адреси чи ключа. Ідентифікатор містить від 1 до 64 малих латинських літер або цифр. Кожен ключ має бути окремим випадковим значенням із 32 байтів у Base64.

| Процес | Параметр | Призначення |
| --- | --- | --- |
| API | `Judge__Workers__judge01__CurrentKey` | Ключ ідентичності `judge01`. Для другого Worker створи окрему ідентичність `judge02`. |
| API | `Judge__Workers__judge01__PreviousKey` | Необов’язковий ключ тієї ж ідентичності на час ротації. |
| Worker | `JudgeWorker__ApiBaseUrl` | Базова адреса HTTPS із довіреним сертифікатом. |
| Worker | `JudgeWorker__WorkerId`, `JudgeWorker__Key` | Ідентичність та її ключ. |

Ін’єктуй секрети в середовище сервісів із захищеного сховища. API в Development також читає User Secrets. Для ротації встанови новий Current і попередній Previous, перезапусти API, перемкни ключ Worker і прибери Previous після перевірки. Залишай одну активну копію процесу на ідентичність. [Порівняння ключів у .NET](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.cryptographicoperations.fixedtimeequals?view=net-10.0)

- Перехоплення ключа дає доступ до черги від імені Worker. HTTPS захищає трафік, клієнт перевіряє сертифікат і відхиляє перенаправлення. Якщо TLS завершується на проксі, API довіряє позначці HTTPS тільки від явно дозволеного проксі. Проксі має замінювати вхідні forwarding-заголовки.
- Повтор або підміна запиту обмежуються перевіркою ідентичності, токена видачі й серверного часу. Ключі перевіряються в постійному часі. Журнали Worker містять технічні типи помилок та ID завдань. Ключі й токени потребують редагування в HTTP-логах проксі або засобів діагностики.
- Якщо API або мережа недоступні, Worker чекає 2, 4 і далі до 30 секунд між повторними спробами. Тайм-аут запиту 10 секунд. За порожньої черги пауза 5 секунд, під час резервування heartbeat виконується кожні 15 секунд. Зупинка сервісу скасовує локальні запити, після чого відновлення lease належить API.

## Схема й SQL GRANT

`20261107162834_AddJudgeLeases` додає до наявної `dbo.Submissions` поля `JudgeWorkerId varchar(64)`, `JudgeLeaseToken uniqueidentifier`, `JudgeLeaseExpiresAtUtc datetime2`, `JudgeAttemptCount int` з default 0, `JudgeStartedAtUtc datetime2` і `JudgeFinishedAtUtc datetime2`. Інші нові поля nullable. Початок позначає останню видачу. Статус і час завершення готують мінімальний запис результату. Два CHECK обмежують лічильник і узгодженість lease. Два фільтровані індекси підтримують відновлення прострочених видач і єдиного власника. Спроба зі старим `Running` та порожнім lease може відновитися як прострочена при claim.

Для вже налаштованого `CodeRankAPI` з `SELECT, INSERT` на `dbo.Submissions` новий дозвіл складається з `UPDATE` для наведених семи стовпців. Блок також показує мінімальні права читання для Judge-операцій у разі налаштування з нуля. Звір database user, якому відповідає login, у погодженій тестовій БД. `sys.sp_getapplock` з `@DbPrincipal='public'` доступна членам стандартної ролі `public`. Окремий процес Worker під’єднується лише до HTTPS API. [Дозволи на об’єкти SQL Server](https://learn.microsoft.com/en-us/sql/t-sql/statements/grant-object-permissions-transact-sql?view=sql-server-ver17)

```sql
GRANT CONNECT TO [CodeRankAPI];
GRANT SELECT (Id, ProblemId, Language, Status, JudgeWorkerId, JudgeLeaseToken,
    JudgeLeaseExpiresAtUtc, JudgeAttemptCount, JudgeFinishedAtUtc)
    ON OBJECT::dbo.Submissions TO [CodeRankAPI];
GRANT UPDATE (Status, JudgeWorkerId, JudgeLeaseToken, JudgeLeaseExpiresAtUtc,
    JudgeAttemptCount, JudgeStartedAtUtc, JudgeFinishedAtUtc)
    ON OBJECT::dbo.Submissions TO [CodeRankAPI];
```

1. Підготуй погоджену ізольовану БД із синтетичними спробами, резервну копію та DBA-сесію. Звір `DB_NAME()`, наявність `dbo.Submissions` та рядка `20261107144141_AddSubmissions` у `dbo.__EFMigrationsHistory`.
2. У копії [AddJudgeLeases.sql](../database/migrations/AddJudgeLeases.sql) задай ім’я погодженої БД у `@ExpectedDatabase` і виконай весь скрипт в одному сеансі. Він перевіряє історію, додає лише метадані lease, індекси та обмеження в транзакції. Повторний запуск звіряє наявність об’єктів.
3. Звір шість колонок, два CHECK, два фільтровані індекси, рядок історії й початкові записи. Надай відсутні права та звір SET-параметри фільтрованих індексів для з’єднання CodeRankAPI. Після міграції запускай нову збірку API й виконай QA. EF використовує додані колонки також при звичайному записі Submission. [Вимоги до фільтрованих індексів](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)
4. Якщо потрібне повернення до попередньої збірки, збережи колонки й історію. EF rollback припиняється, коли в БД є спроби видачі або статус `Running`.

## Запуск і ручний QA

Збери переносимий пакет командою `dotnet publish worker/CodeRank.Judge.Worker -c Release -p:UseAppHost=false`. На Ubuntu потрібен shared runtime `Microsoft.AspNetCore.App` 10.x. Запуск із каталогу публікації через `dotnet CodeRank.Judge.Worker.dll` використовує параметри із середовища процесу. Worker цього етапу підтримує lease до зупинки або його втрати. Для QA використовуй виділену чергу з синтетичними спробами. [Документація .NET Worker](https://learn.microsoft.com/en-us/dotnet/core/extensions/workers)

1. На порожній черзі перевір `204`. Звір `401` для JWT, неправильного ключа та незахищеного запиту. Для HTTP-перевірки використай лише спеціальний QA-ключ.
2. Надішли одну синтетичну спробу. З двох незалежних Worker ID одночасно виконай claim, за можливості через два екземпляри API з тією самою MSSQL. Очікуй один `200` і один `204`. Повтори claim власника й звір той самий lease та незмінний лічильник.
3. Перевір heartbeat, перезапуск API й повторне підключення Worker з тим самим ID. Зупини його, дочекайся закінчення lease і виконай claim з іншого ID. Новий токен має відрізнятися, старий heartbeat дає `409`. Після трьох прострочених видач звір `SystemError` та наявність запису в історії студента.
4. На ізольованій БД потримай `CodeRank.JudgeQueue.v1` у другому SQL-сеансі довше 5 секунд. Звір `503` і успішний повтор після звільнення. Перевір мережевий збій Worker та відсутність ключів і токенів у журналах. Сценарії запису вердиктів запускаються в автоматизованих тестах.

## Наступний етап. Sandbox

1. Підготуй Ubuntu Server 24.04 LTS у VirtualBox на Windows 11. Початкові ресурси 4 vCPU та 6–8 ГБ RAM, один Submission одночасно. Вимкни спільні папки, буфер обміну й перетягування. Мережевий доступ залиш для окремого довіреного процесу Worker до HTTPS API. [Посібник безпеки VirtualBox](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/Security.html)
2. Компілюй і запускай код у середовищі з окремим непривілейованим UID, ізольованими процесами, файлами й мережею. Обмеж CPU, пам’ять і кількість процесів через cgroup v2. Додай ліміт часу, розміру виходу і тимчасових файлів, фільтрацію системних викликів та завершення всього дерева процесів. Робочий каталог належить одній спробі. Середовище коду має бути відокремлене від Windows-хоста, MSSQL і конфігурації Worker, зокрема JWT та машинного ключа. [Документація Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)
3. Зберігай версійовані приватні тести в окремому сховищі з доступом довіреного компонента за Problem ID. Публічні ProblemExamples призначені для умови. Runner передає лише ввід поточного тесту і зберігає очікуваний результат поза процесом користувача.
4. Перед увімкненням вердиктів перевір доступ до файлів, мережі, секретів і хоста, зростання пам’яті, процесів та диска, тайм-аут, вбивство нащадків і очищення робочого каталогу. Використовуй багатошарову ізоляцію VM і процесу. Під’єднай реальні результати після проходження цих перевірок.
