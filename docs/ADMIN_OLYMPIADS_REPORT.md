# SCRUM-12 — адміністрування олімпіад

Реалізацію підготовлено у `feature/admin-olympiad-management` від синхронізованої `develop` на коміті `306aeac727d131d97a97ef8c2ad8203b0502f6f4` після PR №14. Адміністратор може створити чернетку, відредагувати її, керувати задачами й опублікувати олімпіаду. [SCRUM-12](https://coderank.atlassian.net/browse/SCRUM-12)

## Що змінилося

- Backend додає `AdminOlympiadsController`, окремі DTO та політику `ActiveAdmin`. Політика перевіряє поточного користувача за `sub` токена і читає його роль та активність із `Users` під час запиту. Запити без чинного токена отримують `401`. Звичайний, деактивований або відсутній у БД користувач із чинним токеном отримує `403`.
- Нові записи одразу є чернетками. Автора визначає сервер. Список показує власні й спільні олімпіади, включно з чернетками, з ознакою `isOwn`. Активні адміністратори керують олімпіадами спільно, зокрема коли первинний автор більше не активний.
- Для додавання доступні задачі, автори яких мають роль `Admin` у БД. Задачі інших адміністраторів входять до спільного каталогу. Нова прив’язка задачі звичайного користувача дає `404`. Якщо такий зв’язок вже існував, адміністратор може приховати або від’єднати його. Назва цієї задачі у DTO дорівнює `null`, а публікація олімпіади з видимим таким зв’язком дає `409`.
- Frontend додає список і створення на `/admin/olympiads` та редактор на `/admin/olympiads/:id`. Посилання на керування з’являється у профілі після підтвердження ролі через API. Форми показують завантаження, порожній стан, помилки та повторне завантаження. Публікація і зняття з публікації потребують підтвердження.
- Backend працює з наявними `Users`, `Olympiads`, `OlympiadProblems` і `Problems`. Публічні маршрути SCRUM-8 читають опубліковані олімпіади й лише видимі зв’язки. Реєстрація видає роль `User`, а авторизація Problems CRUD далі обмежує запис власником.

## Контракт API

Базовий шлях `/api/v1/admin/olympiads`. Для всіх операцій потрібен Bearer JWT активного адміністратора.

| Метод і шлях від базового | Тіло запиту | Успішна відповідь |
| --- | --- | --- |
| `GET /` | — | `200`, масив олімпіад від найпізнішого початку, потім за ID |
| `GET /{id}` | — | `200`, `{ olympiad, problems: { revision, items } }` |
| `GET /problems` | — | `200`, каталог доступних для додавання задач `[{ id, title }]` |
| `POST /` | `{ title, description, startsAtUtc, endsAtUtc }` | `201`, олімпіада і `Location` на адмін-деталі |
| `PUT /{id}` | `{ title, description, startsAtUtc, endsAtUtc }` | `204` |
| `PUT /{id}/problems` | `{ revision, items: [{ problemId, position, maxPoints, isVisible }] }` | `200`, збережені `{ revision, items }` у порядку `position` |
| `PUT /{id}/publication` | `{ isPublished }` | `204` |

Олімпіада у відповіді містить `id`, `title`, `description`, `startsAtUtc`, `endsAtUtc`, `isPublished` та `isOwn`. У списку збережених зв’язків кожен елемент додатково містить `title` задачі. ID додатні. Назва після обрізання пробілів містить 1–200 символів. Дати передаються у форматі UTC з суфіксом `Z`, завершення має бути пізніше початку. Поля часу у формі позначені UTC.

Для збереження задач передай ревізію з останнього читання та повний бажаний список. Новий ID додає зв’язок, зміна полів оновлює його, вилучений ID від’єднує задачу. Порожній список від’єднує всі задачі від олімпіади. `position` і `maxPoints` мають бути додатними 32-бітними цілими, `isVisible` — логічним значенням. Пропуски між позиціями допустимі. Дублікати позицій або задач дають `409`. Два елементи можна поміняти місцями одним запитом.

Заміна зв’язків виконується в одній транзакції `Serializable`. Операція звільняє зайняті позиції для змінених або вилучених зв’язків, а потім записує нові значення. У разі збою весь пакет відкочується. Застаріла ревізія дає `409`, якщо збережений стан відрізняється від запитаного. Повтор запиту з уже застосованим результатом повертає поточний стан. Від’єднання змінює лише `OlympiadProblems`.

`400` означає некоректний формат або значення. `404` означає недоступну олімпіаду чи задачу. У `409` API повертає короткий `code`, зокрема `duplicate_position`, `duplicate_problem`, `stale_links`, `concurrent_change` або `unavailable_visible_problem`.

## Мінімальні SQL-права для адмін-API

У сесії DBA для **CodeRankSeedTest** звір права саме database user, якому відповідає login `CodeRankAPI`, і надай лише відсутні права. Блок нижче описує доступ для нових маршрутів. Публічний перегляд умов також потребує чинних прав читання SCRUM-8 на `Problems` та `ProblemExamples`. [Синтаксис GRANT у Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/grant-object-permissions-transact-sql?view=sql-server-ver15)

```sql
IF DB_NAME() <> N'CodeRankSeedTest'
    THROW 50001, N'Відкрий CodeRankSeedTest для QA.', 1;

GRANT CONNECT TO [CodeRankAPI];
GRANT SELECT (Id, Role, IsActive) ON OBJECT::dbo.Users TO [CodeRankAPI];
GRANT SELECT (Id, Title, CreatedByUserId) ON OBJECT::dbo.Problems TO [CodeRankAPI];
GRANT SELECT, INSERT ON OBJECT::dbo.Olympiads TO [CodeRankAPI];
GRANT UPDATE (Title, Description, StartsAtUtc, EndsAtUtc, IsPublished)
    ON OBJECT::dbo.Olympiads TO [CodeRankAPI];
GRANT SELECT, INSERT, DELETE ON OBJECT::dbo.OlympiadProblems TO [CodeRankAPI];
```

`DELETE` потрібен тільки на таблиці зв’язків. Запуск схеми й наповнення тестових даних належать окремому обліковому запису з відповідними дозволами. Права `db_owner` для API зайві.

## Ручна перевірка на CodeRankSeedTest

1. Спрямуй локальний Backend на `CodeRankSeedTest` через локальні секрети. Підготуй активного адміністратора, звичайного користувача, адміністратора, якого можна деактивувати після входу, дві задачі адміністраторів і одну задачу звичайного користувача. Використай наявний тестовий seed або погоджені тестові записи. [Налаштування БД](DATABASE_SEEDING.md)
2. Запусти `dotnet run --project backend/CodeRank.Api --launch-profile https` з кореня репозиторію й `npm run dev` після `npm ci` в `frontend`. Увійди як Admin, відкрий керування з профілю й створи чернетку з префіксом `SCRUM-12 QA`. Перевір `201`, відображення чернетки та відсутність її у публічному каталозі. Спробуй однакові або переставлені дати, очікуй відхилення.
3. Відредагуй назву, опис і дати. Додай дві задачі зі спільного каталогу, задай бали, позиції та видимість, збережи. Перестав дві задачі місцями за один запис. Спробуй однакові позиції та підстановку ID задачі звичайного користувача через API. Очікуй `409` і `404` відповідно та звір збережені зв’язки.
4. Відкрий редактор у двох вкладках. Збережи зміну в першій, потім іншу зміну з попередньою ревізією у другій. Очікуй `409`. Онови другу вкладку й перевір результат першої операції.
5. Спершу відхили діалог публікації й перевір стан чернетки. Підтвердь публікацію та відкрий каталог як відвідувач. Перевір доступ до видимої задачі та `404` для прихованої. Від’єднай одну задачу й перевір, що її запис у `Problems` існує. Зніми олімпіаду з публікації та перевір `404` для її публічних URL.
6. Повтори адмін-запити без токена, із токеном User та із раніше виданим токеном деактивованого Admin. Очікуй `401`, `403` і `403`. У звичайного користувача мають працювати вхід, власні задачі й перегляд опублікованих олімпіад. У DevTools імітуй втрату мережі при відкритті адмін-списку й перевір повтор після відновлення.
