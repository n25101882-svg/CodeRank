# Olympiads Read API — CodeRank

Перша Backend-функція практичної №8: читання опублікованих олімпіад із наявної таблиці `dbo.Olympiads` через `CodeRankDbContext` та EF Core. Обидва маршрути публічні (`[AllowAnonymous]`), Bearer Token для цих запитів не потрібний.

## Ендпоінти та контракт

| Метод і шлях | Результат |
|---|---|
| `GET /api/v1/olympiads` | `200 OK` і масив опублікованих олімпіад; сортування `StartsAtUtc ASC`, потім `Id ASC` |
| `GET /api/v1/olympiads/{id}` | `200 OK` для опублікованого запису; `404 Not Found` для відсутнього або неопублікованого запису |

`id` має тип `long`. Порожня таблиця або наявність лише неопублікованих записів дає `200 OK` із `[]`. Додаткового відбору за поточною датою немає: опубліковані минулі та майбутні олімпіади доступні однаково.

Окремий DTO `OlympiadResponse` містить лише `id`, `title`, `description`, `startsAtUtc`, `endsAtUtc`. `description` може бути `null`. EF Entity, `IsPublished`, `CreatedByUserId`, `CreatedAtUtc` і навігаційні властивості не повертаються. Обидва запити використовують `AsNoTracking`, спільний фільтр публікації та проєкцію DTO, асинхронне виконання і `CancellationToken`.

Поля дат уже представляють UTC у SQL-first моделі. Оскільки MSSQL `datetime2` не зберігає часовий пояс, при формуванні DTO їм явно встановлюється `DateTimeKind.Utc`; числове значення дати не перетворюється. У JSON вони серіалізуються з `Z`.

### Приклад списку

Наведені значення ілюструють контракт, а не підтверджують вміст користувацької БД.

```json
[
  {
    "id": 101,
    "title": "CodeRank Demo Contest",
    "description": "Демонстраційна олімпіада з програмування.",
    "startsAtUtc": "2030-06-01T10:00:00Z",
    "endsAtUtc": "2030-06-01T12:00:00Z"
  }
]
```

### Приклад одного запису

```json
{
  "id": 101,
  "title": "CodeRank Demo Contest",
  "description": "Демонстраційна олімпіада з програмування.",
  "startsAtUtc": "2030-06-01T10:00:00Z",
  "endsAtUtc": "2030-06-01T12:00:00Z"
}
```

Неопублікований запис не відрізняється від відсутнього за HTTP-статусом і не розкривається у відповіді.

## Локальна перевірка

Наявні Connection String і JWT Signing Key налаштовуються лише на Backend за [AUTH_API.md](AUTH_API.md). Публічний доступ до нових маршрутів не скасовує обов’язкової JWT-конфігурації та перевірки підключення до БД при старті API. SQL-користувач API повинен мати `SELECT` на `dbo.Olympiads`; зміна дозволів цією фічею не виконується.

З кореня репозиторію:

```powershell
dotnet build backend/CodeRank.Api/CodeRank.Api.csproj
dotnet run --project backend/CodeRank.Api --launch-profile https
```

В іншому терміналі, із довіреним локальним HTTPS-сертифікатом:

```powershell
curl.exe -i https://localhost:7160/api/v1/olympiads
# Вкажіть Id опублікованого запису зі списку:
curl.exe -i https://localhost:7160/api/v1/olympiads/101
```

`101` — лише приклад Id, він може дати 404 у конкретній БД. Ці GET-запити не додають і не змінюють записи. Якщо Backend уже працює, для нових маршрутів потрібен перезапуск із новою збіркою.

## Ручна інтеграційна перевірка з Microsoft SQL Server

Ручну інтеграцію виконано з окремою тестовою БД `CodeRankAuthTest`. Нижче наведено підтверджені результати цієї перевірки, окремо від автоматизованих SQLite-тестів.

| Перевірка | Підтверджений результат |
|---|---|
| `GET /api/v1/olympiads` | `200 OK` |
| `GET /api/v1/olympiads/{id}` для опублікованої олімпіади | `200 OK` |
| `GET /api/v1/olympiads/{id}` для неопублікованої олімпіади | `404 Not Found` |
| `SELECT`-доступ SQL-користувача `CodeRankAPI` до `dbo.Olympiads` | Доступ підтверджено |

Під час виправлення зауважень PR #10 ці ручні запити повторно не виконувалися; дані БД, SQL-дозволи, User Secrets та конфігурація підключення не змінювалися.

## Автоматизовані перевірки

Нові HTTP-тести розміщено в наявному `CodeRank.Api.Auth.Tests`, який уже перевіряє Auth, CORS і валідацію. Використано спільний `AuthApiFactory`: справжні контролери й middleware у TestServer та окрема SQLite in-memory БД на кожен тест. Підключення і джерело JWT-ключа замінено тестовими; до MSSQL тести не звертаються.

```powershell
# Нові тести:
dotnet test tests/CodeRank.Api.Auth.Tests/CodeRank.Api.Auth.Tests.csproj --filter FullyQualifiedName~OlympiadsReadApiTests
# Повний набір Auth / CORS / validation / Olympiads:
dotnet test tests/CodeRank.Api.Auth.Tests/CodeRank.Api.Auth.Tests.csproj
# Регресія Seeder:
dotnet test tests/CodeRank.Api.Seeding.Tests/CodeRank.Api.Seeding.Tests.csproj
```

Якщо запущений API блокує звичайний output, до `build` і `test` можна додати `--artifacts-path <окремий-локальний-каталог>`, щоб не зупиняти цей процес.

### Фактичні результати

| Перевірка | Результат |
|---|---|
| `dotnet build` Backend | Успішно, 0 помилок і 0 попереджень |
| Окремий запуск `OlympiadsReadApiTests` | 13/13 успішних |
| Повний HTTP-набір Auth / CORS / validation / Olympiads | 93/93: 80 попередніх + 13 нових |
| Регресійний набір Database Seeder | 26/26 успішних |
| Разом у двох повних наборах | 119/119, без невдалих або пропущених тестів |

13 нових тестів перевіряють публічний доступ, відбір опублікованих записів, порожній результат за наявності лише чернеток, обидва ключі сортування, порожню таблицю, отримання одного запису, nullable-опис та UTC-дати, відсутні/неопубліковані Id і точний набір полів DTO для обох маршрутів. Окремий запуск цих 13 тестів не додається повторно до загальних 119.

Збірку й тести фактично виконано з .NET SDK 10.0.401 / runtime 10.0.12 та окремим `--artifacts-path` поза репозиторієм. Початковий запуск VSTest зупинився до тестів через недоступне локальне з’єднання з testhost; після дозволу мережевого доступу й налаштування тимчасового каталогу повторний і обидва повні запуски успішні. TRX-журнали збережено локально; реальні MSSQL-БД у цих запусках не використовувалися.

Після виправлення зауважень PR #10 збірку та обидва повні набори повторено: 0 помилок і 0 попереджень збірки, HTTP — 93/93, Seeder — 26/26, без невдалих або пропущених тестів. У HTTP-набір входять усі 13 тестів `OlympiadsReadApiTests`.

## Межі реалізації

Додано тільки два GET-ендпоінти. Пагінацію та операції Create/Update/Delete не додавали. SQL-схема, моделі, міграції, JWT, CORS, Seeder і Frontend залишаються без змін. Підтверджені результати ручної MSSQL-інтеграції наведено окремо; автоматизовані тести використовують ізольовану SQLite і не підключаються до реальних MSSQL-БД.
