# CodeRank — звіт із тестування Authentication та валідації реєстрації

## 1. Мета тестування

Перевірити збереження несекретних чернеток Login/Register після F5, їх очищення після успіху та відсутність пароля у Web Storage. Зберегти результати перевірок реєстрації, Login, захищеного профілю та JWT-валідації CodeRank; усунути приймання суто числових імен та очевидно слабких нових паролів. Переконатися, що некоректний запит відхиляється на Backend навіть без браузера, а невдала реєстрація не створює Users або UserProfiles.

У звіті розмежовано попередні ручні перевірки, підтверджені користувачем, поточні автоматизовані перевірки та сценарії з недостатніми доказами. PASS означає виконання описаних умов конкретного тесту, а не гарантію безпеки всієї системи. FAIL збережено для відтворених дефектів; NOT RUN також використано, коли результат згадано, але його неможливо достовірно встановити.

## 2. Відомості про проєкт CodeRank

CodeRank — вебплатформа для олімпіад із програмування. Backend: ASP.NET Core Web API / .NET 10, EF Core 10.0.12, SQL-first модель Microsoft SQL Server. Frontend: HTML, CSS, Vanilla JavaScript, Vite 8.3.5. Робоча гілка — `feature/auth-frontend`.

Об’єкти перевірки:

- POST `/api/v1/auth/register` — реєстрація з email, password, firstName, lastName;
- POST `/api/v1/auth/login` — перевірка облікових даних і видача JWT;
- GET `/api/v1/users/me` — отримання актуального активного користувача за перевіреним JWT;
- маршрути Frontend `/login`, `/register`, `/dashboard`.

Контракти й попередній ручний JWT-аудит наведено в [AUTH_API.md](AUTH_API.md); запуск Frontend — у [Frontend README](../frontend/README.md).

## 4. Обсяг тестування

### Реалізовані правила

- Ім’я та прізвище обов’язкові, до 100 UTF-16 одиниць, як у `StringLength` Backend; повинна бути хоча б одна Unicode-літера. Порожні, пробільні, числові й суто пунктуаційні значення відхиляються. Апостроф U+02BC сам по собі не вважається літерою імені. Українські та інші Unicode-літери, комбіновані знаки, апострофи, дефіси й пробіли підтримуються. Вимога не є whitelist усіх допустимих символів імені.
- Новий пароль має довжину 12–128 UTF-16 одиниць. Перевіряються локальний набір 326 публічних SHA-256-компараторів поширених значень, повторення короткого мотиву довжиною 1–8 символів щонайменше двічі та прості циклічні числові послідовності. Випадкові непослідовні цифрові паролі не заборонено.
- Для порівняння слабкості використовується окрема копія: NFKC, спільний набір крайових пробільних символів та згортання ASCII-регістру. Числові блоки Unicode визначено спільними даними. Початковий пароль не обрізається, не нормалізується й без змін передається до `PasswordHasher<User>`.
- SHA-256 у [спільних даних політики](../shared/validation/registration-policy.json) служить лише для lookup публічного blocklist. Це не механізм зберігання паролів користувачів. Зовнішні сервіси перевірки паролів не викликаються.
- Нові правила застосовано лише до Register DTO та форми реєстрації. Login і дані вже створених акаунтів не змінювалися. Немає вимог до обов’язкової великої літери, цифри чи спеціального символу.

Перевірка поширених значень без обов’язкового змішування класів символів відповідає цьому підходу [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html). Це не заява повної відповідності стандарту: у CodeRank збережено заданий мінімум 12, локальний blocklist обмежений, Rate Limiting залишається відкритим дефектом.

Перевірено нову валідацію, відсутність часткових записів, незмінність пароля перед хешуванням, сумісність старих Login, CORS і попередні Auth/Seeder-сценарії. Не виконувалися зміни SQL-схеми, міграції, очищення чи виправлення наявних даних. Нові реєстрації в реальній CodeRankAuthTest під час цього прогону не створювалися.

### Чернетки форм — CR-UX-001

- `coderank.draft.login`: лише email; `coderank.draft.register`: лише firstName, lastName, email. Збереження виконується під час input/change у sessionStorage, відновлення — через властивості input.value при відкритті форми та reload.
- Пароль ніколи не входить до дозволеного набору полів, зокрема після натискання «Показати пароль». У localStorage чернетки не записуються; повний FormData/DTO не серіалізується до Web Storage.
- Успішна реєстрація очищає Register-чернетку; успішний Login та Logout очищають обидві чернетки. Невдала спроба зберігає несекретні поля для повторення. Токен зберігається окремим механізмом.
- Невідомі поля, некоректні типи та пошкоджений JSON відкидаються. За недоступного сховища форма залишається придатною до введення; відновлення чернетки за таких умов неможливе.

## 6. Знайдені дефекти — Bug Reports

| Bug ID | Опис | Severity | Status |
|---|---|---|---|
| CR-SEC-001 | Відсутнє обмеження частоти Login-запитів | High | Open |
| CR-UX-001 | Втрата введених несекретних даних після F5 | Low | Verified |
| CR-VAL-001 | Приймання суто числових імен | Medium | Verified |
| CR-SEC-002 | Приймання очевидно слабких паролів | Medium | Verified |

CR-VAL-001 і CR-SEC-002 позначено Verified після успішних прямих Backend HTTP-тестів, Frontend unit- і браузерних перевірок. Це автоматизоване підтвердження; поточний ручний MSSQL-retest має NOT RUN. Історичні FAIL TC-011/012 залишені для опису дефектів до виправлення.

CR-UX-001 виправлено й позначено Verified після 8 нових unit-тестів, 8 нових browser-сценаріїв на двох viewport та окремого повторення попередньої F5-діагностики. Тепер firstName, lastName та email відновлюються; пароль залишається порожнім і не потрапляє до Storage. Історичний FAIL збережено в A, актуальний PASS — у D. Відновлення пароля не є метою виправлення.

CR-SEC-001 не виправлявся; обробка HTTP 429 у Frontend не означає наявності серверного Rate Limiting. Точний темп і кількість попередніх невдалих Login-запитів невідомі, тому висновки про конкретний поріг не робляться.

## 9. Загальні висновки

Валідацію реєстрації посилено на Frontend і Backend. Автоматизовано підтверджено відмову суто числовим іменам та вибраним класам слабких паролів, підтримку Unicode-імен, збереження обмежень довжини та відсутність записів після HTTP 400. Початкові паролі перед хешуванням не змінюються; старі акаунти продовжують проходити Login.

Чернетки готові до повторної ручної перевірки. Backend у поточному UX-етапі не змінювався; якщо попередню серверну валідацію ще не завантажено, перед її ручним retest потрібно перезапустити API. Користувацький Frontend на 5173 не зупинявся. CR-UX-001 тепер Verified, CR-VAL-001 і CR-SEC-002 залишаються Verified. CR-SEC-001 (Rate Limiting) залишається Open. Відкладений ручний XSS-сценарій має NOT RUN. Для підміни sub з 2 на 1 зафіксовано лише перенаправлення на Login; HTTP-код потребує підтвердження через Network. Не виконано новий ручний MSSQL-прогін, повний penetration test, перевірку всіх Unicode-обходів або всіх SQL Injection/JWT-атак. Одинична відмова SQL-подібному паролю й перевірені Unicode-приклади не є доказами повної відсутності таких вразливостей.

SQL-схему, міграції, User Secrets і наявні дані користувачів не змінювали. Commit, Push і Merge не виконувалися.
